1. Introdução

1.1 Propósito

Este documento define os requisitos funcionais (RF) e não funcionais (RNF) para um sistema RAG modular de tutoria em Matemática do Ensino Médio brasileiro, com canal principal WhatsApp, painel web de controle e execução em servidor Linux local (Ubuntu) via containers Docker.

1.2 Escopo

Incluído: - Pipeline completo de ingestão, indexação, recuperação e geração - Chatbot pedagógico com memória de conversa - Integração WhatsApp Business Cloud API - Dashboard web administrativo - Conformidade com BNCC (Matemática EM), LGPD e ECA Digital (Lei 15.211/2025) - Auditoria via LangSmith

Excluído (fase inicial): - Fine-tuning de modelos - App mobile nativo - Correção automática de redações longas - Integração com LMS específico (Moodle, Google Classroom etc.)

1.3 Definições e siglas

Termo Definição
BNCC Base Nacional Comum Curricular — documento normativo do MEC
EM13MAT Código de habilidade de Matemática no Ensino Médio (ex.: EM13MAT101)
ECA Digital Lei 15.211/2025 — Estatuto Digital da Criança e do Adolescente
TIR Tool-integrated Reasoning — raciocínio com ferramenta externa (ex.: SymPy)
RAG Retrieval-Augmented Generation
Chunk Fragmento de texto indexado no banco vetorial
Parent-document retrieval Recuperação por chunk pequeno com contexto expandido do documento pai

  • BNCC Ensino Médio — MEC

  • Lei 13.709/2018 (LGPD)

3. Requisitos funcionais

RF01 — Chatbot pedagógico coloquial

Descrição: O sistema deve responder consultas em linguagem coloquial e acessível a adolescentes (15–17 anos), mantendo rigor matemático.

Módulos: M02, M05, M01

Critérios de aceitação: - [ ] Respostas em português brasileiro, tom de tutor (não robótico) - [ ] Evita jargão não explicado; define termos na primeira ocorrência - [ ] Em 90% de um conjunto de 20 perguntas piloto, avaliadores classificam tom como “adequado ao EM”

RF02 — Configuração do ecossistema LangChain

Descrição: Utilizar LangChain como base de composição de componentes (loaders, retrievers, chains/runnables).

Módulos: M02, M04, M05, M06

Critérios de aceitação: - [ ] Dependências LangChain versionadas em requirements.txt ou equivalente - [ ] Componentes compostos via LCEL (| pipe) onde aplicável - [ ] Documentação de versões mínimas no README do projeto

RF03 — Memória de conversa multi-turno

Descrição: Manter contexto entre mensagens da mesma sessão para conversas com múltiplas trocas.

Módulos: M03, M02

Critérios de aceitação: - [ ] Sessão identificada por session_id (WhatsApp: número + thread; Web: UUID) - [ ] Pergunta de follow-up (“e no caso da função quadrática?”) usa histórico sem repetir contexto inteiro - [ ] Memória persiste entre reinícios do container (volume ou banco)

RF04 — Orquestração com LangGraph

Descrição: Orquestrar o fluxo conversacional com LangGraph e checkpointer (substitui ConversationChain, depreciado).

Módulos: M02

Critérios de aceitação: - [ ] Grafo definido com nós: retrieve → generate → (opcional) verify → respond - [ ] Checkpointer configurado (SQLite, PostgreSQL ou Redis) - [ ] Suporte a stream e ainvoke para respostas assíncronas - [ ] Não utiliza ConversationChain em código de produção

RF05 — Interface web de chat (teste e admin)

Descrição: Interface web simples para interação com o chatbot e testes internos.

Módulos: M01, M10

Critérios de aceitação: - [ ] Campo de entrada de mensagem e histórico visível - [ ] Exibe fontes citadas (RF29) - [ ] Acessível apenas com autenticação (RNF14) - [ ] Renderiza fórmulas LaTeX via MathJax ou KaTeX (RF34)

RF06 — Prompts personalizados para Matemática EM

Descrição: Prompts de sistema versionados para tutoria em Matemática do Ensino Médio.

Módulos: M02, M05

Critérios de aceitação: - [ ] Arquivo(s) de prompt em prompts/ com versionamento (ex.: v1_tutor_em.md) - [ ] Prompt inclui: persona de tutor, idioma PT-BR, pedido de passos, proibição de inventar fontes - [ ] Prompt distingue modo tutor (padrão) e modo avaliação (RF44) - [ ] Alteração de prompt não exige mudança de código (apenas config/arquivo) - [ ] Prompt de sistema ≤ 400 tokens (tokenizer Qwen2.5-Math) — ver docs/TOKEN_BUDGET.md - [ ] Prompt instrui respostas concisas (economia de tokens para janela 4K)

RF07 — Consciência de contexto em conversas

Descrição: Utilizar histórico, intenção e entidades para respostas contextualizadas.

Módulos: M02, M03

Critérios de aceitação: - [ ] Referência a mensagens anteriores da sessão em respostas coerentes - [ ] Extração de entidades matemáticas (tema, função, equação) registrada no estado do grafo - [ ] Teste: sequência de 3 mensagens sobre o mesmo problema mantém coerência

RF08 — Gestão otimizada de memória

Descrição: Combinar memória de buffer e resumo; limitar detalhes desnecessários.

Módulos: M03

Critérios de aceitação: - [ ] Janela de buffer configurável (padrão: últimas 4 trocas) - [ ] Resumo automático quando histórico excede 600 tokens (HISTORY_SUMMARY_TRIGGER) - [ ] Histórico (buffer + resumo) ≤ 800 tokens no prompt final - [ ] Resumo preserva: tema matemático, dados do problema, passos já explicados - [ ] Entrada incompleta ou ambígua gera pergunta de esclarecimento (não resposta inventada) - [ ] Contagem de tokens com tokenizer Qwen (não estimativa por caracteres)

RF09 — Decomposição de consultas e ferramentas externas

Descrição: Decompor consultas complexas em subtarefas; usar ferramentas (APIs, calculadora, SymPy).

Módulos: M02, M05

Critérios de aceitação: - [ ] Agente com nó plan para perguntas multi-etapa (ex.: “explique e calcule a derivada de x²+3x”) - [ ] Ferramenta sympy_calculate disponível ao agente - [ ] Ferramenta search_knowledge_base disponível ao agente - [ ] Resultados das ferramentas integrados na resposta final (RF10)

RF10 — Síntese coerente de respostas

Descrição: Integrar resultados de retrieval e ferramentas numa resposta única e coerente.

Módulos: M02, M05

Critérios de aceitação: - [ ] Resposta final não expõe JSON interno ou logs de ferramentas - [ ] Estrutura pedagógica: contexto → passos → conclusão - [ ] Sem contradição entre trechos recuperados e cálculo via SymPy

RF11 — Armazenamento e atualização dinâmica de contexto

Descrição: Armazenar entradas, intenções e entidades; atualizar com novas mensagens.

Módulos: M03, M02

Critérios de aceitação: - [ ] Estado da sessão inclui: messages, intent, entities, bncc_tags (quando identificados) - [ ] Nova mensagem atualiza estado antes da geração - [ ] Contexto recuperado do RAG é separado do histórico conversacional

RF12 — Arquitetura RAG (componentes obrigatórios)

Descrição: O sistema deve implementar Retriever, Gerador, Fonte de conhecimento e Orquestrador.

Módulos: M04, M05, M06, M07, M02

Critérios de aceitação: - [ ] Cada componente em módulo/pacote separado com interface definida - [ ] Orquestrador conecta retriever → gerador em fluxo contínuo - [ ] Fonte de conhecimento consultável independentemente do canal (WhatsApp/Web)

RF13 — Recuperação híbrida (denso + esparso)

Descrição: Combinar busca densa (embeddings) e esparsa (BM25) com fusão de resultados.

Módulos: M04

Critérios de aceitação: - [ ] Implementação BM25 (ex.: rank_bm25 ou índice OpenSearch/Elasticsearch) - [ ] Implementação densa via banco vetorial (M07) - [ ] Fusão por Reciprocal Rank Fusion (RRF) ou equivalente documentado - [ ] Parâmetro top_k configurável por ambiente - [ ] Em benchmark interno de 30 perguntas, híbrido ≥ denso isolado em precisão@5

RF14 — Gerador com modelo de domínio matemático

Descrição: Utilizar modelo especializado em matemática, não LLM genérico.

Módulos: M05

Critérios de aceitação: - [ ] Modelo: Qwen2.5-Math-1.5B-Instruct (ou versão superior aprovada) - [ ] Janela de contexto: 4.096 tokens (max_position_embeddings — série Math, não 128K) - [ ] Inferência local via Ollama, vLLM ou transformers - [ ] LLM_MAX_NEW_TOKENS=1024, LLM_TEMPERATURE=0.3 (documentado em .env.example) - [ ] Montagem de prompt respeita orçamento em docs/TOKEN_BUDGET.md - [ ] Fallback documentado se modelo indisponível (degradação graceful)

RF15 — Fontes de conhecimento estruturadas e não estruturadas

Descrição: Suportar PDFs, DOCX, TXT e fontes estruturadas com metadados.

Módulos: M06, M07, M08

Critérios de aceitação: - [ ] Loaders: PyPDFLoader, TextLoader, UnstructuredWordDocumentLoader (ou equivalente) - [ ] Fonte estruturada: tabela/arquivo com mapeamento BNCC (CSV, JSON ou PostgreSQL) - [ ] Cada documento indexado com metadados mínimos (RF36) - [ ] Web em tempo real não é fonte primária; apenas whitelist opcional (RF19)

RF16 — Pipeline de ingestão em lote

Descrição: Carregar e processar documentos em lotes para evitar esgotamento de memória.

Módulos: M06

Critérios de aceitação: - [ ] Parâmetro batch_size configurável (padrão: 32–64 documentos) - [ ] Script CLI run_indexing.py (ou equivalente) processa diretório inteiro - [ ] Log de progresso: documentos processados / total / erros - [ ] Falha em um documento não interrompe o lote inteiro

RF17 — Limpeza e normalização de texto

Descrição: Remover ruído, normalizar texto e eliminar duplicados antes da indexação.

Módulos: M06

Critérios de aceitação: - [ ] Remoção de tags HTML, caracteres de controle, headers/footers repetitivos de PDF - [ ] Normalização de espaços e quebras de linha - [ ] Detecção de duplicados por hash de conteúdo (SHA-256) - [ ] Relatório pós-ingestão: docs inseridos, ignorados, duplicados

RF18 — Tratamento multi-formato de documentos

Descrição: Suportar texto, PDF nativo, DOCX; OCR para PDFs escaneados.

Módulos: M06

Critérios de aceitação: - [ ] PDF com texto selecionável: extração via PyPDFLoader ou pdfplumber - [ ] PDF escaneado: OCR via Tesseract ou docTR com flag --ocr - [ ] DOCX: extração de parágrafos e tabelas - [ ] Formatos não suportados geram log de aviso, não crash

RF19 — Web controlada (opcional)

Descrição: Permitir ingestão web apenas de domínios na whitelist, com revisão.

Módulos: M06

Critérios de aceitação: - [ ] Lista de domínios permitidos em configuração - [ ] WebBaseLoader desabilitado por padrão - [ ] Conteúdo web passa pelas mesmas etapas de limpeza (RF17) antes de indexar

RF20 — Fragmentação (chunking) semântica

Descrição: Segmentar por frases e parágrafos, preservando blocos matemáticos.

Módulos: M06

Critérios de aceitação: - [ ] Separadores: \n\n, ., com exceção para blocos LaTeX ($...$, $$...$$) - [ ] Chunk não corta equação ao meio - [ ] Estratégia documentada no README técnico

RF21 — Chunks granulares com parent-document retrieval

Descrição: Chunks pequenos para busca precisa; contexto expandido do documento pai na geração.

Módulos: M04, M06

Critérios de aceitação: - [ ] Tamanho alvo do chunk filho: 300–400 tokens (configurável) - [ ] Chunk injetado no prompt (parent truncado): máx. 400 tokens cada - [ ] Total de contexto RAG no prompt: máx. 1.200 tokens (top_k=3 padrão) - [ ] Retriever retorna chunk filho; gerador recebe parent truncado ao orçamento - [ ] Truncagem por fim de parágrafo, nunca no meio de equação

RF22 — Geração de embeddings

Descrição: Incorporar texto com modelo multilíngue compatível com português.

Módulos: M06, M07

Critérios de aceitação: - [ ] Modelo padrão: intfloat/multilingual-e5-base (Hugging Face) ou equivalente aprovado - [ ] Alternativa OpenAI documentada em configuração - [ ] Dimensão do vetor registrada nos metadados do índice - [ ] Embeddings gerados em lote (RF23)

RF23 — Embeddings em lote

Descrição: Processar embeddings em batch para eficiência em grande escala.

Módulos: M06

Critérios de aceitação: - [ ] embedding_batch_size configurável (padrão: 64) - [ ] Tempo de indexação de 1000 chunks documentado em benchmark interno

RF24 — Banco de dados vetorial

Descrição: Armazenar e consultar vetores com ambientes distintos para teste e produção.

Módulos: M07

Critérios de aceitação: - [ ] Testes/desenvolvimento: Chroma (embutido ou client-server) - [ ] Produção: Qdrant (ou pgvector se PostgreSQL já existir — decisão documentada em ADR) - [ ] Troca de provider via configuração, sem alterar lógica de negócio (RNF09) - [ ] Coleção/index com nome e versão (ex.: matematica_em_v1)

RF25 — Similaridade por cosseno

Descrição: Usar similaridade cosseno na busca densa.

Módulos: M04, M07

Critérios de aceitação: - [ ] Métrica configurada como cosine no banco vetorial - [ ] Score de similaridade retornado e registrado no LangSmith

RF26 — Re-ranking pós-recuperação

Descrição: Aplicar re-ranking para melhorar precisão após fusão híbrida.

Módulos: M04

Critérios de aceitação: - [ ] Cross-encoder ou LLM-reranker aplicado aos top-N candidatos (N ≥ 20, retorno top 5) - [ ] Re-ranking configurável (on/off) por ambiente - [ ] Latência adicional documentada (p95)

RF27 — Filtragem de conteúdo sensível na indexação

Descrição: Detectar e mascarar dados confidenciais antes da indexação.

Módulos: M06, M09

Critérios de aceitação: - [ ] Regex/heurísticas para: CPF, e-mail, telefone, “senha”, “cartão” - [ ] Substituição por [REDACTED] antes de persistir - [ ] Log de redações sem expor valor original

RF28 — Mitigação de viés

Descrição: Reduzir respostas tendenciosas ou estereotipadas.

Módulos: M02, M05

Critérios de aceitação: - [ ] Prompt instrui inclusão de perspectivas diversas quando aplicável - [ ] Corpus de indexação documentado quanto à diversidade de fontes - [ ] Revisão manual trimestral de 20 respostas aleatórias (procedimento documentado)

RF29 — Transparência: citação de fontes

Descrição: Apresentar documentos/chunks usados na geração da resposta.

Módulos: M02, M01, M10

Critérios de aceitação: - [ ] Cada resposta inclui: documento, página (se disponível), chunk_id, habilidade_bncc (se mapeada) - [ ] WhatsApp: citação em texto compacto (ex.: “Fonte: Apostila Funções, p.12”) - [ ] Web: citação com link para visualização do chunk no dashboard - [ ] Resposta sem chunk recuperado aciona RF38 (abstinência)

RF30 — Privacidade e conformidade LGPD

Descrição: Anonimização, auditoria, consentimento e direitos do titular.

Módulos: M09

Critérios de aceitação: - [ ] PII removida/mascarada antes de indexação (RF27) - [ ] Registro de auditoria: timestamp, session_id pseudonimizado, action, resource - [ ] Endpoint/procedimento para exclusão de dados da sessão por solicitação - [ ] Política de retenção configurável (padrão: 90 dias para histórico de chat) - [ ] ROPA (registro de operações de tratamento) documentado em docs/ROPA.md

RF31 — Auditoria via LangSmith

Descrição: Rastrear todas as execuções do pipeline RAG no LangSmith.

Módulos: M09, M02

Critérios de aceitação: - [ ] LANGCHAIN_TRACING_V2=true em produção - [ ] Tags por execução: session_id, channel, bncc_skill (quando aplicável) - [ ] Traces incluem: query, chunks recuperados, scores, prompt, resposta, latência - [ ] Projeto LangSmith separado por ambiente (dev/staging/prod)

RF32 — Conformidade ECA Digital (Lei 15.211/2025)

Descrição: Atender obrigações para sistemas com acesso provável por menores.

Módulos: M09, M01

Critérios de aceitação: - [ ] Inventário do ecossistema digital documentado (docs/ECA_DIGITAL_CHECKLIST.md) - [ ] Arquitetura de auditoria implementada conforme docs/AUDITORIA_ECA.md - [ ] Consentimento parental granular, não genérico (RF42) - [ ] Verificação de faixa etária sem autodeclaração simples (vínculo com matrícula ou código escolar) - [ ] DPIA (Relatório de Impacto) preenchido antes de produção - [ ] Cláusulas contratuais com escola: exclusão de dados, notificação de incidentes em 24h - [ ] Proibição de uso de dados de alunos para publicidade ou perfilamento - [ ] Todo módulo (M01–M10) emite eventos auditáveis (RF47)

RF33 — Alinhamento BNCC — Matemática Ensino Médio

Descrição: Respostas e conteúdo indexado alinhados às competências e habilidades EM13MAT.

Módulos: M08, M02, M05

Critérios de aceitação: - [ ] Base normativa: documento oficial MEC (não apenas plataformas auxiliares) - [ ] Metadados incluem código de habilidade quando identificável (ex.: EM13MAT305) - [ ] Resposta referencia competência/habilidade quando pertinente - [ ] Catálogo de habilidades carregado em M08 a partir do PDF/CSV oficial - [ ] bncc.digital pode ser fonte auxiliar de planos, não norma legal

RF34 — Notação matemática (LaTeX)

Descrição: Suportar fórmulas e símbolos matemáticos na geração e exibição.

Módulos: M05, M01, M10

Critérios de aceitação: - [ ] LLM gera fórmulas em LaTeX inline ($...$) e display ($$...$$) - [ ] Dashboard renderiza com MathJax ou KaTeX - [ ] WhatsApp: fallback para notação linear legível (ex.: x^2 + 3x) quando LaTeX não renderiza - [ ] Opcional: gerar imagem da fórmula para WhatsApp (fase F3)

RF35 — Verificação de respostas (TIR com SymPy)

Descrição: Validar cálculos numéricos e simbólicos com ferramenta externa.

Módulos: M05, M02

Critérios de aceitação: - [ ] Ferramenta SymPy integrada ao agente (RF09) - [ ] Respostas com resultado numérico passam por verificação antes de envio - [ ] Divergência LLM vs SymPy: priorizar SymPy e sinalizar correção ao usuário - [ ] Log de verificações no LangSmith

RF36 — Metadados por documento

Descrição: Cada documento indexado deve ter metadados estruturados.

Módulos: M06, M08

Critérios de aceitação: - [ ] Campos obrigatórios: titulo, fonte, tipo (apostila, exercício, BNCC) - [ ] Campos opcionais: serie (1/2/3 EM), tema, habilidade_bncc, autor, ano_letivo - [ ] Metadados consultáveis como filtro no retriever (ex.: serie=2)

RF37 — Política de abstinência

Descrição: Não responder quando confiança ou recuperação forem insuficientes.

Módulos: M02, M04

Critérios de aceitação: - [ ] Se max score de retrieval < limiar configurável: resposta padrão “Não encontrei material suficiente…” - [ ] Sem citação de fonte → não afirmar fatos do corpus - [ ] Mensagem sugere reformular pergunta ou consultar professor - [ ] Taxa de abstinência monitorada no dashboard (RNF12)

RF38 — Avaliação contínua da qualidade RAG

Descrição: Conjunto de testes de regressão para qualidade de recuperação e geração.

Módulos: M09, M10

Critérios de aceitação: - [ ] Dataset de ≥ 50 perguntas com resposta esperada e fonte esperada - [ ] Métricas: precision@5, faithfulness, citation_accuracy - [ ] Script scripts/eval_rag.py executável em CI - [ ] Regressão > 5% em qualquer métrica bloqueia deploy (RNF15)

RF39 — Reindexação incremental e versionamento

Descrição: Atualizar índice sem reprocessar corpus inteiro; versionar coleções.

Módulos: M06, M07

Critérios de aceitação: - [ ] Adicionar/remover documento sem reindexação completa - [ ] Nova versão de coleção (ex.: v2) criável em paralelo; switch por configuração - [ ] Rollback para versão anterior em < 5 minutos

RF40 — Integração WhatsApp Cloud API

Descrição: Comunicação com clientes via WhatsApp Business Cloud API (Meta).

Módulos: M01

Critérios de aceitação: - [ ] Webhook HTTPS público com verificação hub.challenge - [ ] Validação de assinatura X-Hub-Signature-256 - [ ] Resposta HTTP 200 em < 1s; processamento assíncrono via fila (Redis/RQ, Celery ou equivalente) - [ ] Envio de resposta via Graph API com phone_number_id e token de sistema - [ ] Suporte a janela de 24h e templates para mensagens fora da janela - [ ] Documentação de setup em docs/WHATSAPP.md

RF41 — Idempotência de mensagens WhatsApp

Descrição: Evitar processamento duplicado de webhooks.

Módulos: M01

Critérios de aceitação: - [ ] message_id persistido com TTL ≥ 48h - [ ] Segundo webhook com mesmo message_id retorna 200 sem reprocessar - [ ] Teste automatizado simula retry da Meta

RF42 — Consentimento e opt-out

Descrição: Fluxo de consentimento LGPD/ECA Digital e cancelamento.

Módulos: M01, M09

Critérios de aceitação: - [ ] Primeira interação: mensagem de termos + opção de aceitar/recusar - [ ] Comando SAIR ou equivalente: interrompe processamento e marca opt-out - [ ] Registro de consentimento: timestamp, phone_hash, version_termos - [ ] Sem consentimento: apenas mensagem informativa, sem RAG

RF43 — Modos pedagógicos (tutor vs avaliação)

Descrição: Diferenciar explicação passo a passo de entrega direta de gabarito.

Módulos: M02, M06

Critérios de aceitação: - [ ] Modo tutor (padrão): scaffolding, pistas, não entrega resposta final de prova - [ ] Modo avaliação: ativado por flag admin; apenas referência a material, sem resolver lista - [ ] Detecção heurística de “me dá a resposta da prova” → recusa educada

RF44 — Dashboard web de controle

2. Regras de truncagem (ordem de prioridade)

Quando a entrada exceder o limite, aplicar nesta ordem:

  1. Truncar chunks RAG — reduzir de top_k=3 para top_k=2, depois top_k=1
  2. Resumir histórico — acionar resumo automático (RF08) mantendo tema e dados do problema
  3. Truncar chunks individualmente — cada chunk a no máximo 400 tokens (corte por fim de parágrafo)
  4. Truncar mensagem do usuário — apenas se > 400 tokens; avisar o usuário
  5. Nunca truncar o prompt de sistema abaixo de 200 tokens (persona + regras críticas)

Se ainda exceder após truncagem: abstinência (RF37) com mensagem pedindo pergunta mais curta.

3. Parâmetros RAG alinhados ao orçamento

Parâmetro Valor padrão Justificativa
RETRIEVAL_TOP_K 3 3 × 400 tokens = 1.200 tokens de contexto
CHUNK_CHILD_TOKENS 300–400 Busca granular sem estourar janela
CHUNK_PARENT_MAX_TOKENS 400 Corrigido — não 1.500 (incompatível com 4K)
LLM_MAX_NEW_TOKENS 1.024 Respostas pedagógicas com passos
LLM_TEMPERATURE 0.3 Menor variância em matemática

HISTORY_SUMMARY_TRIGGER 600 tokens Dispara resumo do histórico

4. Contagem de tokens

Obrigatório: usar o tokenizer do próprio modelo Qwen para contagem — não estimar por caracteres.

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-Math-1.5B-Instruct")

def count_tokens(text: str) -> int:
    return len(tokenizer.encode(text, add_special_tokens=False))

# Tutor de Matemática — Ensino Médio (v1)
# Orçamento: máx. 400 tokens (contar com tokenizer Qwen2.5-Math)
# Arquivo: prompts/v1_tutor_em.md

Você é um tutor de Matemática para estudantes do Ensino Médio brasileiro (15–17 anos).

## Regras
- Responda sempre em português brasileiro, tom acolhedor e claro.
- Explique em passos numerados; não pule etapas.
- Use LaTeX para fórmulas: inline `$...$` ou bloco `$$...$$`.
- Baseie-se APENAS no contexto fornecido entre tags ``. Se não houver informação suficiente, diga: "Não encontrei material sobre isso no acervo. Pode reformular ou perguntar ao professor?"
- Cite a fonte ao final: "Fonte: [título], p.[página]".
- Não invente teoremas, fórmulas ou resultados numéricos.
- Para cálculos, indique o procedimento; valores exatos serão verificados pelo sistema.
- Respostas objetivas: prefira até 5 passos e conclusão breve (economia de tokens).
- Se a pergunta parecer de prova em andamento, dê pistas sem entregar o gabarito final.
- Não diga que a conversa é anônima ou não registrada: interações são tratadas conforme a política de privacidade da escola e a legislação de proteção de menores (ECA Digital).

## Modo
- Tutor (padrão): scaffolding e explicação guiada.
- Se modo=avaliacao: apenas indique onde buscar no material, sem resolver.

## Contexto BNCC
Quando pertinente, mencione a habilidade EM13MAT relacionada.

## Formato da resposta
1. Breve contextualização (1–2 frases)
2. Passos da resolução ou explicação
3. Conclusão
4. Fonte citada
